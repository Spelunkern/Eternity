## Root frame contract (02-world coordination)

For each live primary zone and idle cadence tick, the root holds the same serialized zone lease across the entire sequence: call `vertical_mobs_idle_frame(root, map_index, now, startup_init.random, world)` exactly once; if it succeeds, immediately call the world-owned `RuntimeZone::update_mob_population` exactly once for that same zone and `now`, with the actual startup pool/Init ports and the real obelisk and linked respawn providers. That method owns regular respawns, static-map obelisk respawns, and linked-group respawns in that order. The mob frame owns AI traversal and `update_deaths` only; it must never invoke population or respawn itself. If the lease is unavailable, do not update population for that zone. Do not interleave other zone mutation between these portions. The nested lease in the mob entry point uses the same recursive serialized root; the outer root lease must remain held through both portions. This split preserves the `CZone::UpdateMobIdle` 00421a00 ordering. `MobPrimaryZones::tick` is the actual obelisk respawn callback inside this population pass; it must not also run as a separate frame operation. Attack and instance-zone scheduling remain separate dependencies.

## Exact single-frame composition and scheduler correction

Correction to the earlier handoff: `MobPrimaryZones::tick(map, now)` calls `MobAppliedSkillsObeliskMaps::tick`, which executes `update_obelisk_respawns`. It is the static-map obelisk respawn portion of `CZone::UpdateMobRespawn`, not an independent timer to run at another cadence. Calling it both before/after the frame and as the population callback duplicates that portion.

At each due idle tick, root holds a `MobPrimaryZoneLease` for the actual map and performs the following inside its `visit` callback, with `now`, the retained `MobInitPorts init`, its shared random, the root's actual pool, and the actual linked-world services:

```cpp
if (!vertical_mobs_idle_frame(root, map_index, now, init.random, mob_world))
    throw /* lost primary route; do not run population */;
zone.update_mob_population(root.mob_pool(), init, now,
    [&](std::uint32_t t) {
        if (!root.tick(map_index, t))
            throw /* lost actual obelisk route */;
    },
    [&](std::uint32_t t) {
        zone.linked_mobs->update(zone.map->definition, *zone.mobs,
            root.mob_pool(), init, t, linked_world);
    });
```

`RuntimeZone::update_mob_population` invokes the obelisk callback only for static maps, after regular population, then invokes the linked callback; never invoke `root.tick` elsewhere for this respawn pass. The outer lease must span the entire sequence; the nested leases use the same recursive root serialization. The idle dispatcher retains each current actor through its dispatch as specified below. No snapshot traversal, second population invocation, or concurrent zone mutation may be inserted between steps.

Original evidence: `ps_game.exe CWorldThread::Update` 00407390, instructions 00407623..00407672, compares the supplied tick unsigned against the idle deadline, calls `CZone::UpdateMobIdle` 00421a00 for each zone when due, then sets the next deadline to the supplied tick plus 1000 ms (DWORD wrap); it does not catch up missed intervals. `UpdateMobIdle` calls `UpdateMobDeath` then `UpdateMobRespawn` after AI traversal. `CZone::UpdateMobRespawn` 0041d240 calls `CMap::UpdateRespawnObelisk` 00429da0 only for a static map, followed by `UpdateBothMobRespawn` 0041b870. The individual obelisk records also have their own recovered due-time gates inside that call. Attack is a separate 500 ms scheduler pass, not part of this callable idle frame. Startup and scheduler deadline initialization still require the actual world owner; this contract does not invent them.

## Current-actor retention checkpoint

`vertical_mobs_idle_frame` now calls `MobPool::retain_during` around each actual pooled mob callback. Nested holds share one per-object count. `MobPool::release` on a held, unlinked object defers AI cleanup and return to the available pool until the final hold exits; allocation during the callback cannot reuse that identity. Repeated release and reentry of a pending-release subject are rejected. The final hold releases even when the callback throws. The guard uses the existing pool and membership owners, with no second actor registry; its retention bookkeeping is host lifetime protection and its delayed cleanup is not claimed as original-execution behavior. Pool, zone and services must outlive all callbacks, and calls remain serialized. Other dispatch paths that need actor retention must explicitly adopt this guard; a primary-zone lease alone is not sufficient.
