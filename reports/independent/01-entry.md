## Single-load persistence integration

Read-only inspection of `independent/09-persistence` at `c0ebb2bca692fa1e87140808f438a6fa2cd0331f` shows `vertical_persistence_select` calls `Players::load` itself and returns `VerticalPersistenceSelection`, containing both the snapshot and the retained `CharacterReplica`. Do not call it after `vertical_entry_select`: that would load the same character twice, updating JoinDate again and potentially consuming gift notifications before the second snapshot.

Two integration routes are available, subject to review of the persistence branch: (1) keep `vertical_entry_select` as the sole SQL loader and have its `loaded(PlayerSnapshot)` callback retain that snapshot, call `vertical_persistence_restore_with_products(snapshot, products, max_grow, inventory_pool, skills, quests, points)`, and pass the same retained snapshot to `ActorLoadPipeline`; or (2) call the existing `request_character_selection` gate with a DB callback that invokes `vertical_persistence_select` once, retain its returned snapshot and replica, and build the actor from that snapshot. In route (2), do not also invoke `vertical_entry_select`, which owns its own `Players::load` call. The account's `PointItemStore`, actual replica pools, and returned replica must use the real DB-user owner's lifetime and serialization; the snapshot, actor load rules and scene must outlive `ActorLoadPipeline`. Product loading and replica restoration may throw, and the owner must discard the incomplete selection and use the recovered state-dependent failure lifecycle; no successful entry should be emitted. The persistence implementation currently rejects relocated or overflow inventory pending the original repair path. Coordinator must reconcile these interfaces and validate the composed path after integration; this note does not claim it has been tested.

## Retained roster review

`ps_dbAgent.exe` `CUser::PacketUserChar` 004059e2..00405a32 scans five retained slots in order, stops at the first matching ID, rejects when the rename-count DWORD is signed-positive or remaining-time DWORD is nonzero, then stores the selected ID and posts DB job 7. `DBCharacter::LoadCharacterList` 0041d930 reads rename as an unsigned byte and remaining time as a DWORD and stores them at +3bc4 and +3b94 respectively. Thus `CharacterSummary::rename` and `remaining_time` preserve these decisions for populated slots, including negative remaining time. Its `slots` owner is reused directly, not copied into a competing registry. `vertical_entry_roster_allows` now gates the adapter before `Players::load` and is independently callable by the 09 persistence integration before its own single load.

The original loader clears empty-slot IDs but does not clear the two relevant status fields. Native empty optional slots do not preserve those residues; a zero-ID request that reaches an empty slot raises an explicit error rather than assuming accept/reject. The caller must bind the passed roster to the authenticated account because `CharacterRoster` itself contains no account ID. The real DB-user owner must receive the selected ID before DB job 7 and implement state-dependent failure handling; this adapter does not own that state. `Players::load` separately checks the current database account/server, `Del`, slot, rename, and remaining time. These live SQL checks are stricter than the retained-roster gate if rows change after roster load, so the adapter does not claim complete original stale-state behavior. Reconcile the original load contract before treating that case as equivalent.

The 09 composition must apply `vertical_entry_roster_allows` to the same retained roster before `vertical_persistence_select`, or call `vertical_entry_select` and use `vertical_persistence_restore_with_products` on its snapshot; never call both loading functions.
