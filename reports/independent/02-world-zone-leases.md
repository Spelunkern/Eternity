# Retained instance-zone authority investigation

Code baseline: `f0a0ae2` plus the scheduler evidence commits `5c7f917` and `84d0f68`. No authority implementation was added. The existing owners do not yet expose the original thread-list and wait-user operations required to close, recycle and reopen an instance safely. This is not a completed instance-lease implementation.

## Original behavior

`ps_game.exe` `CWorld::GetZoneByMapID` 00413df0 returns a permanent zone directly or selects/creates an instance through the existing per-map owner, with modes 1–6, party/guild owner maps and rank/house checks. `CWorld::InitZones` 00414870 initializes each map's permanent zone or initial reusable dynamic zone. The existing `ZoneRegistry` implements these selection/startup paths and retains each actual `RuntimeZone` in its own per-map active/pool storage.

Instance disposal is not a generic zone-destructor operation. `ps_game.exe` `CWorldThread::Update` 00407390, instructions 00407a4c–00407bfa, checks dynamic create type and **both** active-user and enter-wait-user counts, applies the map's expiry interval using the zero deadline sentinel, and only then removes the zone from the thread's actual active list. For types 3–6 it removes the actual keyed owner and decrements original counters, removes the zone from its map list, calls `CZone::MapReleaseObject` 0041c3b0, and places the same allocation into its map heap. The next selection can reuse that allocation; generation changes must therefore be native lifecycle protection, not a new selection registry. The check runs on its own `now+1000` deadline. These observations are from the existing read-only Ghidra disassembly/decompilation, not new fixture claims.

## Precise blocker and required integration

`ZoneRegistry::select` already owns active zones and keyed mappings but has no instance-removal or recycling API. `MobPrimaryZones` owns that registry privately, its `MobPrimaryZoneLease` only addresses primaries, and `drain_all` processes primaries only. `ZoneServices::enqueue_wait` can publish a new zone to an external world-thread owner, but there is no corresponding actual thread-list owner or unlink/acknowledgment operation in this worktree. `WorldAdmission` in this branch owns enter-wait lists privately. Coordinator commit `25d85e2` on main adds `update_zone_wait_packets` and reports 1,024 original sequences plus removal traversal; that change is not integrated in this branch. A complete empty-zone/connection-lifetime drain remains missing. `ZoneUsers` and those queues retain borrowed actors. An instance could therefore still be referenced by a thread, wait queue, actor, or reentrant dispatch if the registry recycled it. Simply adding a pointer lease and erasing a vector would not satisfy this assignment's close/deferred release, generation or original-order requirements.

There is an additional failed-cleanup edge: `ZoneRegistry::select` inserts its active and owner entries before `enqueue_wait`; a throwing enqueue can leave the actual selected zone active even though the caller did not receive a handle. A future selection/lease API must account for that existing committed state and require a real, exception-safe enqueue contract; it cannot assume an exception implies no zone exists. Existing partially initialized zones and failed backend release likewise need explicit staged retry without destroying pooled actors before their retained population sources.

Smallest next shared dependency: integrate the actual ordered world-thread active/wait list owner and a serialized, reentrancy-safe detach operation, plus an admission/zone-user quiescence interface that retains the connection and actor. Extend **the same** `ZoneRegistry` with active-instance identification and staged removal/recycling against those owners. Under `MobPrimaryZones`' recursive executor, atomically select using that existing registry and acquire a generation-checked lease; pin it through queueing and membership, mark closing before dispatch, defer physical release while any lease or dispatch exists, unlink the actual thread and map/owner lists in original order, retain old population sources through pool destruction, and only then recycle. On selection of the same pooled allocation increment its generation; reject stale tokens. Failure at each cleanup stage must be retryable without rerunning completed side effects. The callback/owner must be real and explicit; a no-op unlink, a second zone registry, or a thread-list mirror is not an acceptable replacement.

## Coordinator update and thread-list boundary

The coordinator independently regenerated the original scheduler fixture byte for byte. Main commit `25d85e2` adds `WorldAdmission::update_zone_wait_packets`, reported verified against 1,024 original sequences and removal traversal; this branch does not contain it. It resolves waiting-user packet traversal, not active-user/reset-position traversal, lifetime pinning, or thread-list release.

Additional original evidence: `ps_game.exe` `CWorldThread::AddZone` 004072b0 and `CWorldThread::AddWaitZone` 004072f0 each splice the zone's **same** embedded link at offset +8 into their respective actual list under that list's lock. `CWorldThread::Update` 00407390 promotes waiting links to the active list and later removes active links before recycling. `ZoneRegistry::select` here publishes a zone through `ZoneServices::enqueue_wait`, which `MobZoneServices` delegates to an externally supplied callback. The root currently has neither that callback's actual list nor an unlink operation. Adding an independent active/wait list while still calling the existing external enqueue would create a mirror rather than own the original link; it would not prove that the actual queue stopped referring to the recycled zone. The shared integration must replace/bind that enqueue to the single retained scheduler owner, not add a second queue alongside it. No lease or active/wait implementation has been committed in this investigation.
